# 2コンAでマイク録音、Bで本体DAC再生

RP2350はCPU専用カセットとして動作し、2コンのA/BボタンをC6へUSBで送る。
C6はGPIO0のマイク入力を連続変換し、UART経由でPCのファイルへ保存する。
録音時間をC6のRAM容量で制限しない。PCの保存プログラムとC6のUART接続が必要。

2026-11-24最終確認：リレー付き構成でユーザーが録音・再生の成功を確認した。[最終結果と配線・ビルド手順](../../docs/microphone-record-replay-20261124.md)。以下には切り分け途中の記録も残す。

## 操作

1. C6のUARTをPCへ、C6のネイティブUSBをRP2350へ接続する。
2. PCで `python firmware/tools/record_fc_mic.py --port COM12 --outdir recordings` を実行する。
3. FCをONにする。待機画面は青。C6のOLEDは `READY: 2P A/B`。
4. 2コンのAを押して離すと録音開始。画面は赤、OLEDは `RECORDING`。
5. もう一度Aを押すと停止し、WAVと元のADCデータ・結果JSONを保存する。次のAで別の録音を開始できる。
6. Bで直近の正常終了録音を本体DACから再生する。`-clean.wav` があれば優先し、なければ元WAVを使う。再生中は緑。
7. 再生中にBをもう一度押すと停止。Aを押すと再生を止めて新たに録音する。録音中のBは録音を確定してから再生する。
8. 終了はPC側でCtrl+C、FCをOFFにする。

COM番号は接続したC6のUARTを確認して指定する。PCで保存プログラムを起動する前から
Aを押しっぱなしにしていても録音開始しない。一度離して押し直す。
約2フレーム同じ状態が続いた押下を採用し、長押しでは再トグルしない。

## 保存形式と異常時

- 16 ksample/s、モノラル。ADCは12 bitのまま16 bit little endian値として転送。
- WAVは約13 HzのハイパスでDCを除き、固定倍率16で16 bit化。自動音量補正はしない。
- `.u16le` は加工前のADC値。`.json` はサンプル数、波形の範囲、下限・上限到達数など。
- 同時に `-clean.wav` を保存する。実測した13本の狭い帯域を抑える固定フィルターで、自動音量補正はしない。元のWAVも残す。
- このフィルターは16 kHz ADC・460800 baudで測定した個体用。別の基板・クロック・サンプリング条件では `tools/mic_noise_profile.json` を測り直す。
- Aボタンで正常終了し、サンプル数と通信検査が一致した録音だけ `.wav` へ確定する。
- 途中切断やADCデータ欠落では `.partial.wav` として残し、正常終了と区別する。
- コントローラー通信が750 ms途絶えると録音を停止。PCからの生存通知が3秒途絶えると録音を停止して通常ブリッジへ戻る。
- UARTは待機時115200 baud。明示的な `0x03 + MIC2 ARM\n` で460800 baudへ移り、録音モード終了時に115200へ戻る。
- 音声パケットには連番・長さ・FNV-1aを付け、PCで照合する。

## ハードウェア

マイク入力は既に組んだAC結合・バイアス回路をC6 GPIO0へ接続する。
カセット45番のマイクを含む音声入力を取得する。R7の代わりにリレーのCOM/NCで45番と46番を接続する。
コイルはC6 GPIO1・220Ω・NPNの駆動回路で制御する（BC337等を検討。最終実装型番は未確認）。GPIO1 HIGHで接点を開き、LOWで接続する。
ベースとGNDの間は8.2kΩ（または10kΩ）。コイル電源の電流容量・電圧・サージ抑制素子は別途確認する。
起動・待機・再生・エラー終了時はGPIO1 LOW。録音開始前にHIGHへ変え、20 ms待ってADCを開始する。
GPIO1の初期化はArduinoの`digitalWrite`/`pinMode`順序に依存させず、SDKで出力ラッチをLOWにしてから
入力・出力を有効にし、プルアップを無効化、プルダウンを有効化する。
フラッシュ40 MHz設定とこのGPIO初期化を、IDFの優先初期化テーブルの先頭から実行する。
リンク結果で優先テーブルの最初のエントリーがこの関数を指すことを確認した。
Arduino 3.3.12では出力設定前の`digitalWrite`が無視されるため、以前のLOW設定順序を修正した。
2回のENリセットで`RELAY BOOT gpio1=0`と、その後の読み戻し0を確認。検査中にHIGH指示は送っていない。
ROM/ブートローダーが動くアプリ実行前の区間まで、アプリのログだけで電圧を保証するものではない。
再生中はADC録音をしない。本体の音声は45番→NC接点→46番を経由してテレビへ戻る。
APUのパルス・三角波・ノイズ・DMCは停止し、再生時だけ$4011へ7 bit PCMを書き込む。無音時は64に固定する。
PCスピーカーによる回り込みやマイク回路自体の雑音を除去する機能はない。

2026-11-24の組立試験では、コイルをC6の3V3端子へ接続した状態でOLED消灯が報告され、
UARTでもBrownout detectorによるC6再起動を反復確認した。OLEDだけの問題としては扱わない。
この切り分け段階ではユーザーがリレー配線をいったん全部外した。その後の配線・LED極性修正を経て、リレー再接続で録音・再生成功を確認した。長期安定性は未検証。
コイルを未給電にしたCOM/NCの2線だけでも、先に本体DACの音声経路を試験できる。
この仮接続では録音時の自動切断は働かず、マイク音がテレビへ回り込む可能性がある。

## 再生データと検査

PCで16 kHz / 16 bit WAVを31 tapのアンチエイリアスFIRへ通し、2分の1に間引いて7 bitへ量子化する。
短いフェードを両端に入れ、音量正規化はしない。実際のDAC更新は224 CPU cycles/サンプル（NTSC約7990 Hz）。
再生時のみ既定4倍の固定ゲインを使い、DAC範囲の75%を超えるピークは連続なソフトリミッターで抑える。
`--playback-gain` で倍率を指定できる。録音WAVやADC原本は変更しない。
公称8 kHzとの差は約0.12%。元録音ファイルは変更しない。

RP2350は8192サンプルのリングを持ち、空き容量・消費数をPCへ返す。
PC→UART→C6→USB→RP2350と少しずつ補充し、録音全体をRP2350のRAMへ読み込まない。
入力パケットには位置・長さ・FNV-1aを付ける。バッファ不足・不正データでは停止し、古い音を繰り返さない。

6502の実行検査で、A/Bの読み取りを含めて224 cycles/サンプルを確認。
実際のCリング処理をホストで実行し、100000サンプルの順序・ラップ・終了・不足時停止・位置異常・チェックサム異常を検査。
PC側は奇数長WAV、変換数、7 bit範囲、先頭・末尾の無音、アップロードの位置とチェックサムを確認した。
実機でのB再生とリレー連動は、これらのソフトウェア検査とは分けて確認する。

### 2026-11-24 実機試験の途中経過

リレー配線をユニットごと外し、45番と46番はユーザーが直接ジャンパーした。
C6は無負荷のGPIO1テストを200 ms実行してLOWへ戻り、4秒間の確認中にはBrownoutを検出しなかった。
コイル負荷を戻した際の動作を確認したわけではない。

その後、GPIO1を2秒HIGH・2秒LOWで3回切り替える診断を追加し、
読み戻し1/0と最後のLOW、および診断中にC6の再起動がないことを確認した。
当初ユーザーにはリレーの動作音が聞こえなかったが、LEDの極性を修正した後の再試験では
動作音を確認。ユーザーはトランジスタではなくLEDの逆接続が原因だったと報告した。
修正前後でトランジスタの型番・コイル直列抵抗等を同一条件に保った比較とは限らないため、
各部品の故障や定格への適合まで確定したものとは扱わない。
通常のA録音・B再生へ戻し、DP100 7.5 V設定で起動、PC受信待機を確認した。

最初のB再生では、PCから55296サンプルの転送・RP側の消費完了を確認したが、ユーザーには声が聞こえなかった。
続く最大振幅に近い3秒の440 Hz WAV（24000サンプル）でも、消費完了した一方、ユーザー報告は連続音ではなく短い音だった。
したがって、ファイルの消費完了だけでは本体DACの正常再生と扱わない。

次の比較版は、サンプルをPIO返信形式の32 bit値で事前にリングへ置き、
CPU側へ返す返信を、消費数・終了判定・監査処理より先にPIOへ渡す。
CPUが実際に$4011へ書いた値も受動観測し、直前に返した7 bit値との不一致数と値の範囲をUSB経由で報告する。
高速返信・監査版の実機試験で、3秒の440 Hzについて$4011への書き込み24000回、
値の範囲9～119、期待値との不一致0件を確認。ユーザーも3秒の連続音を確認した。
旧版では実書き込み値を採っていないため直接の前後比較ではないが、応答タイミングが原因だった可能性を支持する。
通常動作は診断音の指定を外し、最新録音の再生へ戻す。

続く実際の録音（ノイズ低減版、55296出力サンプル）でも、$4011の実書き込み55296回、
値の範囲13～108、不一致0件を確認。ユーザーは声を確認したが小さいと報告。
PC側の再生変換へ4倍ゲインとソフトリミッターを追加した。
同一録音で7 bit変換後のRMSは3.45→13.11カウント、約11.59 dB増加。
ユーザーが「十分聞こえる・音割れも気にならない」と確認した。
この時点の構成は45/46直接ジャンパー、リレーは未接続であり、リレー連動の成功とは区別する。

RP2350はCPUデータバスGPIO0～7だけを駆動する。PPU・ミラー制御・GPIO44の音声出力は駆動しない。
FC電源監視GPIO46と既存の電源断保護を使う。
追加のボタン配線は不要。

`build.ps1` でRP2350用 `mic_controller.uf2` を生成する。
C6は既存の `firmware/wifi_bridge/build_bridge.ps1` でビルドする。
TinyUSB 0.21と既存CPU PIOを使い、他の動画・ゲーム・NSF用ファームは変更しない。

## オフライン回帰検査

リポジトリのルートで、pyserialを導入してから実行する。個人の録音は使わない。

```powershell
python firmware/mic_controller/tests/test_pc_audio.py
cc firmware/mic_controller/tests/test_playback.c -O2 -o test_playback
./test_playback
```

Python検査は通信破損の拒否、分割フィルターの連続性、奇数長WAVの変換と再生対象の選択を確認する。
C検査は実装の `playback.h` を直接読み込み、10万サンプルのリング循環、終了、不足、位置異常とチェックサム異常を確認する。
