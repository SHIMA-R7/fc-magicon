# ゲーム選択メニューと大容量ROM

## 実機で進んだ構成（2026-11-21）

メニューからマリオ3と夢の泉を選択し、両方のタイトル画面を実機で確認した。
夢の泉の実プレイ試験は失敗。初回は説明アニメーションで白画面になり音だけ継続、
キャッシュ範囲変更後はアニメーションが進むものの表示異常が残り、ステージをプレイできなかった。
本体RESETでも改善しなかった。タイトル表示をプレイ可能の証拠として扱わない。
保存保持は引き続き未実装であり、タイトル表示を完全互換の意味で扱わない。

使用フラグは `FC_GAME_LIBRARY=ON`、`FC_GAME_FAST_NROM=ON`、
`FC_GAME_PROVEN_MMC3=ON`、`FC_GAME_PRG_SRAM=ON`、`FC_GAME_UNCACHED_PRG=ON`。
`FC_GAME_BANKED_DMA`、`FC_GAME_FAST_ACK`、`FC_GAME_BUS_TRACE` はOFF。

MMC3は10月13日のCPU応答ループを `mmc3_proven_bus.h` に分けて使用する。
バンクアドレスはロード時に事前計算し、書込み時の外部メモリー参照や除算を避ける。
短いA12 Highを除外する4-M2版IRQ検出と、core0でCHRを32KBのDMA応答表へ展開する経路を使う。
CPU用PIOはACKの待ち方を短縮した `cpu_m2_fast.pio`。
ACK到着後にもM2を確認し、期限切れの応答でデータ線を駆動しない。
メニューには従来の `cpu_m2.pio` を使い、USBからの選択要求は診断トレースなしでも受け取れる。

大容量ROMではCHRをPSRAMに残し、384KBのSRAMをPRGキャッシュへ回す。
現在の比較版は末尾から収まるだけの8KBバンクをSRAMに割り当てる。
夢の泉では16～63番の計48バンク。残り0～15番は外部メモリーを参照するため、
任意の場面で応答が間に合う保証はまだない。タイトルまでのCPU lateACKは0。
CHRの最大1KB展開は記録例で10,324クロック（250MHzで約41.3μs）。
旧方式でCHRを256KB SRAMへ置くとPRGキャッシュが16バンク分しか残らず、
24番・61番・29番などへの移行で停止する比較結果が得られた。

PSRAM初期化は必要な大容量項目を選んだ場合に行い、main内の監視タイマーで保護する。
小さいゲームとメニューの起動ではPSRAM全域検査を待たない。
`test_extended_library.py` は通常のバンク処理・保存CPU経路・PRG優先SRAM構成の3種類を検査する。

実機画像・ログは非公開作業先の `menu-mario3-reseat.*` と `menu-kirby-prg48.*`。
途中、保存していた当時の成功バイナリでも同じ映像の崩れが発生した。
利用者がUSBとカセットを挿し直すと同じバイナリで正常表示へ戻り、
その後に修正版のメニューから両タイトルへ移れることを確認した。
コード変更による不調と接続状態による不調を混同せず、保存バイナリも比較に使うこと。

当初の先頭4＋末尾44バンクの構成では、19番バンクへの移行後に停止した。
末尾48バンクへの変更で説明アニメーションは進んだが、正常なプレイには至らなかった。
`kirby-play-20261121.log`、`kirby-tail48-check.log` に両試験を保存。
最後の試験ではPIOのlateACKが0のまま停止しており、このフラグだけでは
FC側のデータのセットアップ時間や全てのバス問題を保証できない。

FC給電OFFで読み出し時間を測定（DWT読み出しなどの測定処理込み）：
SRAM 5クロック、PSRAM cached 70～74クロック、uncached 47クロック（250MHz）。
`psram-prg-latency.log` に記録した。キャッシュ範囲の変更だけで全PRGを保証する方法は未完成。
保存CPUループへROM専用の早期応答を加えた比較でも、外部PRG主体の起動は失敗した。
この経路ではROM読み出しを統計から省くため、`cpu` カウンターは全CPUサイクル数ではない。
今後は全バンクの応答時間を満たす方式と、ゲーム開始後の映像・操作の検証が必要。

現在のVLC/FFmpegプレビューが動作中の場合、別プロセスの直接キャプチャーは
デバイス使用中で失敗する。古いPNGを新しい実機映像として扱わない。

`FC_GAME_LIBRARY=ON` は、起動時にゲーム一覧を出す検証用プロファイル。
従来の `magicon` と同じ配線を使う。90-in-1（mapper 236）は対象外。

- 上下で選択、AまたはSTARTで起動。左右で20件ずつ移動。
- 選択後はFC内蔵RAMのプログラムで約1.5秒待ち、その間にRP2350がゲームを読み込む。
- 再選択はFCの電源を切って入れ直す。FCのRESETだけではメニューへ戻らない。
- 電源を切った後のセーブ保持は未実装。DQ3・夢の泉などの進行保存にはまだ使えない。

## ビルドと格納

通常のSDK設定に `-DFC_GAME_LIBRARY=ON` を加え、`magicon` ターゲットを作る。
このプロファイルはUSBデバイス版。C6のファームは変更しない。

```powershell
cmake -G Ninja -S . -B build_games -DFC_GAME_LIBRARY=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build_games --target magicon
python tools/nes_pack.py --extended --library games.bin --strict <ROMファイル...>
picotool load -v build_games/magicon/magicon.uf2
picotool load -v games.bin -o 0x10800000
picotool reboot
```

書き換え時はFCからカセットを外すかFCをOFFにする。既存フラッシュは先にバックアップする。
ライブラリはフラッシュの8MB位置から最大8MB。動画などの既存データと領域が重なる場合がある。
`--strict` は未対応ファイルがある場合にライブラリ出力を中止する。
`--extended` は対応ファーム専用で、従来版の384KB制限を自動で解除するものではない。
ROMと生成したライブラリ・フラッシュバックアップは公開リポジトリへ入れない。

## 夢の泉（PRG 512KB＋CHR 256KB）

小さいROMは従来どおり内蔵SRAMへ格納する。384KBを超えるROMは最大1MBをPSRAMへ置き、
CHRを内蔵SRAMへ複製する。残るSRAMには先頭のPRGバンクと最終16KBも複製し、
バンク切り替え時はポインターだけを変える。読み出しの際にバンク全体を転送する処理はない。

PSRAMは基板で確認済みのGPIO47だけを使用し、容量を検出する。CSピンの総当たりは行わない。
システムクロック変更後にPSRAMタイミングを再設定する。
FCがOFFのUSB起動時は1MBの書き込み・読み戻し検査を行い、USBシリアルへ結果を出す。
大容量ROMのロード時にもフラッシュとPSRAMの内容を比較する。

2026-11-20時点の確認：接続基板のPSRAM 8MB認識・1MB検査PASS。
ホスト試験で全64 PRGバンク・256 CHRバンク、14本のローダー検査、
各900フレームのシミュレーション、メニューから先頭・夢の泉・末尾への移行を確認。
夢の泉の1面には到達しているが、agnes標準マッパーとの比較では画面下部に差がある。
PSRAMを含む実機速度での動作や全編の正常動作は、この試験では保証されない。

```powershell
python tests/test_cart_audit.py
python tests/test_extended_library.py [手元のROMファイル...]
```

## 実機の黒画面調査（2026-11-20）

初回のプロファイルではツインファミコンでメニューが表示されず、USB先行給電・本体RESETでも改善しなかった。
DP100は利用者指定の7.5V、電流上限1.25Aで操作し、ONは約7.50V・0.36～0.37A、OFFは0Aを実測した。

- 最初のCPU通信はリセットベクタとメニューの初期命令まで正常。その後、命令の実行順序が崩れて停止した。
- `FC_GAME_FAST_NROM=ON` でNROMの余ったSRAMへCPU応答ワードを作り、読み出しと書き込み後の処理を短縮。
- 同プロファイルでNROMのCHRを既存のPIO/DMA方式で応答し、CPUとPPUのARM処理の競合を除いた。
  メニューが毎秒約1,800回の書き込みとパッド値00の記録を継続することを確認。
  EasyCAP再接続後、14件の一覧・カーソル・操作説明が出る実画像も確認した。
- 起動時にA/STARTを押したままでも勝手に起動しないよう、ボタン解放後の押下を要求する。
- 診断ビルド `FC_GAME_BUS_TRACE=ON` では、USBの0～9/a～dで0～13番の起動を要求できる。
  6502はレジスタ$5FF3で要求を受け、通常のRAMスタブへ移る。強制的に稼働中ROMを書き替える方式ではない。
- `FC_GAME_BANKED_DMA=ON` は実験経路。5本のDMAと加算スニファでCHRバンクポインター＋オフセットを作る。
  ポインター更新だけでCHRを切り替える。PIOのアドレス・A13・遅延時の出力禁止はホスト検査済み。
  DMAパイプラインの実機速度と正しい映像は未確認。
- 夢の泉の読込・移行後、CPU応答の期限超過と停止を記録。大容量PRGの速度問題は未解決。
- `FC_GAME_UNCACHED_PRG=ON` は、PSRAMのキャッシュミス時間を避ける比較版。
  最初の版はキャッシュAPIへ絶対アドレスを渡す誤りでロード中に停止した。
  XIP_BASEを引いたオフセットへ修正後はメニュー表示まで確認。夢の泉の正常起動には至っていない。
- main内のライブラリロードへ4秒のウォッチドッグ保護を追加。
  ゲーム選択後の再起動ではUSBが戻らない例があり、SDKのmain前PSRAM初期化も調査対象。
  この保護だけで全ての起動停止から復旧できるとは確認していない。

実験ビルドは上記フラグを明示する。初回プロファイルだけを成功版として再配布しないこと。
キャプチャーは利用者のEasyCAP USB再接続で復帰。直接取得では最初の黒いフレームを避け、
10フレーム以上進めてから保存する。復帰後のメニュー画像は非公開作業先の
`menu-recovery-warm.png`。この段階ではマリオ3・夢の泉の正常表示は未確認だった（後の結果は冒頭参照）。

## CPU ROM DMAの比較と今回の停止点（2026-11-21）

`FC_GAME_CPU_DMA=ON` は未完成の実験機能。通常の成功経路とは分けて扱う。
CPU用PIOを4レーンに分け、各8KBスロットのアドレス生成とメモリー読み出しを
2本ずつのDMAで行う。既存のCHR応答DMA・A12 IRQ検出は残している。
SRAM中心のマリオ3ではDMA比較版のタイトル表示を確認したが、
外部PSRAMのPRG読み出しを含む構成では正常な起動を確認できていない。

`FC_GAME_COPY_RAM=ON` はコード・定数をSRAMに移してフラッシュ競合を避ける比較用。
この場合ROM用SRAMは256KBとなり、384KBの通常構成よりPRGキャッシュが減る。
夢の泉ではCHRだけで256KBを使うため、PRGは全てPSRAM側になる。
この条件でも夢の泉の正常起動には至らなかった。

最新の実験はM2 Low中の先読みと、マッパー書込みHigh中のバンク指定の事前投入。
バンク指定を落とすカウンターは2回から0回へ減ったが、マリオ3も黒画面のままであり、
改善版として配布できる状態ではない。先読み版の `late` / `lateACK` が0でも、
PIOからの期限超過通知を実装していないため正常応答の証拠に使えない。
先読み・共有FIFO・WRAM応答を含む実機タイミングの追加検証が必要。

保存成功版にも生じた共通の映像崩れについて、カセットは挿し直さず、USB給電だけを
完全に外して接続し直すとタイトル表示が復帰した比較結果を得た。
従って接触不良だけと断定しない。保持された電源・リセット状態との関係は未確定。

今回の実機試験はDP100を7.5V / 1.25A設定で使用し、終了時に出力OFFと0mAを確認する。
最後はCPU DMAを使わない保存比較版 `menu-kirby-prg48-title-confirmed.uf2` に戻した。
夢の泉はタイトル表示までの比較結果であり、説明アニメーションと実プレイは未解決。
バッテリーバックアップ保存も未実装。

再開時は、まずこの保存比較版のメニュー・マリオ3表示を基準にし、
PSRAM応答の実効時間とCPUが実際に受け取った値を調べる。
新しいDMA経路とハードの共通症状を同時に変更しない。
実機ログ・画面・ROMは非公開作業先へ保管し、リポジトリには含めない。

ホスト検査は `test_extended_library.py`（実際のcart.cを合成ROMで検査）、
`test_pio_logic.py`、`test_banked_ppu.py`、`test_cpu_rom_dma.py`。
PIO検査はアドレス生成と制御フローを検査するもので、実機のDMA遅延・電気的特性を保証しない。

停止前の最終確認：保存比較版でメニューからマリオ3タイトルを再表示できた。
`final-menu-mario3-control.png/.log` を非公開作業先に保存した。
最終電源確認はDP100出力172mV・0mA・OFF。
上記4本のホスト検査も全て通過した。
