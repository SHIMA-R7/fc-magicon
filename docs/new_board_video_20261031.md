# 新基板：実機動画再生の復旧と検査（2026-10-31）

新Core2350B2、chip ID `7764F3D29FFED4C1`。旧基板の救済配線は使用せず、GPIO35=A9、GPIO36=A10、GPIO43=CIRAM A10、GPIO39=LEDの元配線。ツインファミコン入力へDP100から7.6V、電流設定1.25A。DP100の独立OVP/OCP変更は反映されなかったため、その設定変更を前提とした保護とはしていない。

## 確認した結果

- ダンパー入力25本、180.875秒・6,720 SNAPで誤読・揺れ0。
- CPUデータ出力131,338バイト、CPU入力1,536回、PPU静止出力4,096バイトが全一致。
- FC実機で本体VRAMの52試験が完走し、全試験不一致0・通信エラー0。
- 実動画の先頭フレームのCHR 4,096バイトをFC自身が読み戻し、不一致0。
- 全1,939コマ、242.375秒の動画を終端まで進行。最終pending=0、音声の入力サンプル7,755,968を消費後、PCM128の無音値に切替。再生エラーなし。
- RP基板のUSBをユーザーが外した後、FC給電のみで電源投入を2回実施。両回とも5秒・10秒のキャプチャーで映像の再生を確認した。

全編の全画素を読み戻した検査ではない。全編ではキャプチャーと再生進行ログ、先頭フレームではCHR読み戻しを用いた。

## 修正

1. 元配線用の`standalone_video/baseline/ppu_lookup.pio`で、DMA返信を待つ間に/RDの終了を検出し、期限切れ返信を入力方向のまま消費する。以前の周期の返信を後のネームテーブル読出しへ出さない。32命令。
2. 上記のノンブロッキング待機を最初に実装した際、初期画面の未使用タイル値0を「未受信」と誤認し、返信待ちで停止する回帰を作った。bit31を受信完了マーカーとし、方向ビット8..15とは分離して修正した。方向0のタイルは受信完了と判定するが駆動しない。bits16..23は常に0なので、通常読出しの末尾のOUT PINDIRSで出力を解除できる。
3. CHR読み戻し時の比較用CPU窓$7000-$7FFFにも高速応答を追加。これが遅い状態では、PPUの実測値が原本に一致しているのに比較用値が異なる偽の不一致が出た。高速化後は4KB全一致。

`tests/test_player_ppu_deadline.py`でアドレス形成、160通りの返信遅延、未使用タイル、期限切れ後の復帰を検査。これは命令モデルであり、電気的な過渡現象の再現ではない。旧GPIO39/43救済用PIOは今回の修正・検査の対象外。

この修正や今回の新基板の正常結果から、以前の基板で生じた入力ピン異常の原因まで確定はしない。

## 音声は実音の確認を継続中

最初の大きなキャプチャーノイズを避けるため、PCのプレビュー再生はミュートしていた。録画には音声ストリームを残していた。音声のサンプル進行とGPIO44出力のログは正常だが、それだけで音楽が実際に聞こえることを保証しない。

ユーザーの無音指摘後、ミュートを解除。録画の音楽との照合では明確な一致を確認できず、440Hzの直接PWMテストへ切替。録音には435～445Hzの成分が出たが小さく、音楽出力の成功とはしていない。Windows側のキャプチャー入力と既定再生先はミュートされていなかった。新基板VR1の調整状態についてユーザーへ確認中。

この後、新基板のVR1が最大位置であることをユーザーが確認。直接PWMの440Hzと動画用PIO方式の440Hzは、どちらもユーザーが同程度に聞こえると確認した。PCMの音楽が十分な音量で聞こえることまでは確定していない。

続いてユーザー提供MIDIを本体APUへ変換し、曲の発音をユーザーが確認した。[本体音源版と、その後の横縞対策](native_apu_video_20261031.md)を参照。現在の実機はそちらの全編試験完走版。試験後はFC電源OFF、メディア領域は保持している。
