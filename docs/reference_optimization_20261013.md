# 先例の確認とオフライン最適化

2026-10-13。最初に現在の成果をGitHubへ保存：`1d8eb120bb51923f490e51adfebec7ced656489b`。その後の変更はこの記録にまとめる。実機へは書き込んでいない。

## 参考にした順序

1. [PPUppyの応答処理](https://svn.code.sf.net/p/tom7misc/svn/trunk/ppuppy/ppuppy.cc)：ネームテーブル読出しから粗いY・列を得て、CHRアドレス下位3bitから細かいYを得る。PPUは先読みやスプライト読出しも行うため、単なるタイル行の周回カウンターより情報が多い。既存プロジェクト側は次のサイクルの応答も前もって選んでいる。
2. [PiPUの転送](https://github.com/rasteri/PiPU/blob/master/ppusquirt/ppusquirt.c)：二重バッファとUSB非同期転送を確認。パレットの変更と次の画像の準備をそろえる箇所にはTODOがあり、同期部分をそのまま成功例としてコピーはしない。
3. [PiPUの色変換](https://github.com/rasteri/PiPU/blob/master/ppusquirt/frameprocess.c)：RGBからパレット・色を選ぶ表を事前計算し、メモリで計算時間を節約。元コードの高速経路は固定パレットなので、ここでは考え方だけを参考にし、動的パレットと既存のLab距離を維持した独立実装にする。
4. [NESFlixのMMC3版](https://github.com/no-carrier/NESFlix/blob/master/nesflix_mmc3.asm)：事前に作ったCHRバンクを切り替える再生方式を確認。ネット転送や毎フレームの色変換を解決する方式ではないので、今回の高速化には直接使わない。

第三者のソースはローカルの `ref/` に参照用として保存し、独自ファームへ貼り付けていない。

## 試験1：描画位置をアドレスから求める

`firmware/magicon/remote_position.h` を追加。独立実装で、ネームテーブルのアドレスから粗いY・列、CHRから細かいY・ビット面を得る。属性読出しは位置を変えず、スプライトの$1000側は背景とは別に扱う。未確定位置からはフレームバッファの値を返さない。

4ミラー×30行×32列×8細行×2面の全組合せ試験が合格。Nestopiaのネームテーブル読出しを観測するフックを加え、`FC_REMOTE_NAMETABLE=1` の場合だけこの経路を使った。180枚の合成素材では360表示フレーム、PVでは1,800表示フレームすべてでRGB画素差0。**この経路はエミュの走査線番号を使わない。**

ただし、実機のDMA経路にはまだ接続していない。ソフトウェア上でアドレスから位置を求められたことと、基板でネームテーブルの信号を取り込み、期限内にDMAの参照先を切り替えることは別の試験。このヘッダーだけを追加しても実機動画は改善しない。

## 試験2：画素を変えずにカラー変換を高速化

PC側 `nesframe.py` で、量子化RGB32,768通りとNES64色のLab距離を起動時に計算。選ばれた4パレットから各RGBをどの色番号にするかをキャッシュする。以前の距離式と同じ浮動小数点計算、同じ同点時の選択順を維持。ディザ、パレット探索、属性の選択は変更しない。

PCで約16MiBの距離表と最大4MiBのパレット表を使う。RP2350にこの表を載せる変更ではない。起動時の表作成時間は毎フレームの時間に含めない。

| PV冒頭30秒・900枚 | 変更前 | 変更後 |
|---|---:|---:|
| カラー変換の平均 | 26.86ms | 14.85ms |
| 95パーセンタイル | 31.27ms | 22.31ms |
| 最大 | 43.83ms | 30.36ms |
| 33.33msを超えた枚数 | 31 | 0 |

フレームバッファ、パレット、属性、変換後RGBは変更前と全900枚・バイト単位で同一。画質低下で時間を稼いだ結果ではない。Windows側の一回の測定であり、キャプチャや通信・実機処理時間は含めない。合成180枚でもRGB差0、平均15.19ms・95パーセンタイル20.82ms・締切超過0枚。

## 再検証の基準と結果

再検証の区切りは「画素を変更せず900枚で33.33ms超過0枚」「走査線番号なしの位置検出で全表示フレーム一致」。この二点を満たしたため、指定された[ブルアカ7th PV](https://www.youtube.com/watch?v=U6Wlb18KLrI)の同じ0～30秒を再変換・再表示した。

ローカル成果物：

- `firmware/sim/retroarch-remote-20261013/youtube-U6Wlb18KLrI/transferred-30s-optimized.mp4`
- 同フォルダー `comparison-30s-optimized.mp4`
- `conversion-results.json`、`lut-quality-results.json`、`validation-results-optimized.json`

動画の見た目は前回と同じ。改善したのは処理時間と位置検出の試験経路。音は既存の32kHz PCM16復号・10bit PWM相当。実機録画・実通信での30fpsを示す動画ではない。

## 残る制限

音声・通信モデルも再実行。分割送信は3条件すべてで192,000サンプルをリングへ書き込み、破棄0・10ms以上の無音0。650KB/秒を仮定したモデルでも6秒で95画像にとどまり、PCの色変換を高速化しただけでは同モデルの送信待ちが解消しなかった。受信モデルやWindowsの待機粒度も結果に影響する。

実機側には、ネームテーブル観測の実装、PIO/DMAによる期限内の応答、画像・パレット・属性の一貫した切替が残る。現在の256タイル圧縮と8フレームNT更新の混在も未解決。新しい位置検出モデルを、即実機で動く実装と同一視しない。
