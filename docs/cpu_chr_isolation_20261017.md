## Bank switching comparison

`cpu-chr-banks-a9-gpio39-20261017.uf2` switches PPUCTRL bit 4 every 60 VBlanks. Upper CHR bank contains the bitwise inverse of the lower bank, so the two pattern colours should visibly exchange about once per second. No audio, video decoding, frame upload, dynamic CHR memory update, or mapper IRQ is involved. USB reboot, flash verification and restart succeeded; per-artifact flash JSON records SHA256.

User reports black screen. USB log `cpu-chr-banks-hardware-20261017.log` shows reads continuing and heartbeat/write count increasing about once per second, with CPU late latch zero. This does not prove that the PPU received correct initialization bytes. RetroArch/Nestopia snapshots from the exact `banks.nes` at frames 50, 120 and 180 show the expected pattern; the frame-120 image shows inverted colours. The prior static `pattern.nes` was also verified in RetroArch. This emulator test checks the generated ROM and standard NES PPU behaviour, not the real cartridge responder.

`-BankSwitch -Trace` builds `cpu-chr-banks-a9-gpio39-20261017-trace.uf2`, adding counts and last values of CPU writes to PPU registers, the first 16 observed PPUDATA writes, and PPU PIO/DMA state. It adds overhead to the write-capture path and is a diagnostic comparison, not a timing-neutral observer.

Trace variant flashed after explicit FC-off confirmation, verified and restarted. User reports a slightly lighter black. Log `cpu-chr-banks-trace-hardware-20261017.log`: PPUCTRL and PPUMASK each repeatedly observed as C0, with counts increasing above 1.8 million, while PPUSCROLL/PPUADDR/PPUDATA counts stay zero. The PPU lookup remains in its sampling loop, DMA read address at table base; no rendered pattern accesses apparent. This is inconsistent with intended ROM initialization. Captured write-data values are measured near M2 fall by the existing CPU responder and do not independently prove what the FC PPU latched. The earlier non-trace bank variant had a different write pattern, so instrumentation sensitivity remains possible.

Next prepared artifact: `cpu-chr-banks-a9-gpio39-20261017-capture.uf2`, built with `-BankSwitch -Capture` and without `-Trace`. PIO2 independently observes GPIO0..31 during the first 4096 M2 cycles, retaining the previous sample just before M2 falling. DMA stores samples; after a USB reader attaches, firmware compares selected read data with SRAM PRG and prints first 64 reads and up to 32 mismatches. Observer never configures external outputs or changes CPU responder code. Extra DMA activity and SRAM layout can affect timing; this is not an oscilloscope or a direct measurement of the FC CPU's input threshold/setup margin. Not yet flashed.

Capture variant subsequently flashed after explicit FC-off confirmation and verified. User reports black unchanged. Log `cpu-chr-banks-capture-hardware-20261017.log`: 3098 selected ROM reads, 898 mismatches, unexpected-high mask 00, unexpected-low mask 10. Examples: $8000 expected 78 observed 68; $8001 D8 -> C8; $8003 FF -> EF; $800D 10 -> 00. Reset vector 00/80 is observed correctly. Every logged mismatch is D4 failing High. The observed execution (stack accesses after opcode 68, later returning via interrupt vector) is consistent with corrupted opcodes, not a mere CHR-bank-selection problem. This strongly identifies CPU D4 as the failing signal in this run, but does not distinguish an internal GPIO fault, pad configuration, external loading/short, contact, or marginal electrical timing. Earlier successful static-pattern test and dumper suite remain relevant evidence against assuming a permanent stuck-low pin without further measurement.

D4 mapping verified in hardware specification: GPIO4, module P1-5, FC cartridge contact 39 (unrelated to remapped GPIO39/PPU A9). Next physical check should compare unpowered D4-to-GND resistance with D3/D5, with cartridge removed and all supplies disconnected; inspect/reseat this data contact before increasing drive strength or altering wiring.

After physically separating module P1-5 from the baseboard, user measured baseboard side 25 ohms to GND and module side OL. This locates the measured low-resistance path on the baseboard side, rather than establishing a damaged GPIO4 inside the RP. The before/after observation strongly links this black-screen failure to the board-side D4 low-resistance path and its repair.
