# FC本体単独給電向け・早期応答を統合したPV再生版

ユーザーの「単独で動くVerを作って」に対応した比較版。
USB先行給電版とは別のUF2にした。接続済み実機にはまだ書き込んでいない。
これは単独起動を狙う実装であり、ツインファミコンでの起動成功確認ではない。

## 今回の変更

- `build.ps1 -ColdBoot` / `FC_PLAYER_COLD_BOOT=ON` で生成。
- 起動時に外部端子を入力・プル無しとし、OE overrideもLOWに設定。
- RP2350向けSDK2.3.1の `vreg_set_voltage` は既にVREG更新完了を待っている。
  続いてPOWMAN `VREG_STS.VOUT_OK`を確認し、従来の固定10ms待ちを除去した。
  これはコア電圧レギュレーターの状態確認であり、外部IOVDD/3.3Vの測定ではない。
- 実機成功版の映像・音声と同じ250MHzに設定してからCPU PIOを準備する。
  バス応答開始後にクロックを切り替える処理は入れていない。
- 動画用ドライバー作成・画像変換・USB・全編CRC検査より先に、SRAM上の
  小さなCPU応答ループをコア1で開始する。FC電源を確認し、電源断ガードを
  有効にしてからCPUデータ端子の出力許可とCPU PIOを有効にする。
- 起動ベクタは$8000の48Bブートプログラム。6502が本体RAM$0200に待機コードを
  コピーし、$FFF1=$A5で完了通知、その後RAM上から$FFF0をポーリングする。
- コア0は待機中に通常の動画ドライバー、CHR DMA、ミラーリングを準備する。
  完了をrelease公開し、待機通知も確認したコア1がready=1を返す。
  6502はRAM上の`JMP ($FFFC)`で本来のプレイヤー開始位置$C000へ進む。
- 切替時にCPU PIO、FIFO、コア1を停止・初期化しない。コア1はそのまま
  通常のremote_bus_loopへ移るため、途中の命令・ベクタ読出しを遮らない。
- この版はUSBデバイス機能をコンパイルから外した。PCもUSBホストも不要。
  書換え後のUSB経由リカバリーはBOOTSELを使う。旧USB先行版は別途保存してある。
- 映像/音声の保存形式、7VBlank反転、32kHz PCM8、音声補充遅延ガードは維持。

OTPは書き込んでいない。通常のフラッシュファームウェアとして試せる。

## 検査

実際の早期応答Cコード・6502ブートコード・動画ドライバーを接続して検査。

1. 最初のFC読出し前にプレイヤー準備完了でも、ブートから正しく移行。
2. 本体RAMで待っている間に通常プレイヤーを作り直しても待機を維持。
3. 公開後に$C000のプレイヤーが起動し、全99秒・792枚を7VBlankで反転。
4. NMI最大1779CPUサイクル、NTSC VBlank予算2273以内。
5. PCMリングの折返し・EOF無音・200ms遅延検出、メディア検査、時刻モデルも成功。

Pico SDK2.3.1 / ARM GCC15.2.1 Releaseビルド成功。ELFのearly_bus_loop、
remote_bus_loop、48Bのfc_boot_codeがSRAMに配置され、USB stdioシンボルはない。
CPUの早期応答関数は最適化でループ内に展開されている。

これらはプロトコルとコード配置の検査。RP boot ROM / C runtimeを含む電源投入からの
時間、最初の$FFFC/$FFFDに対するバス上の応答期限、電圧/電流は測定していない。

## 実機で残る条件

FC本体から給電するには、現在未実装のD1などの給電経路が必要。
ただしD1だけでは、RPのIOVDD立上り前にFC側信号が入力される問題を解決しない。
GPIO入力化/OE禁止もその電圧を遮断しない。電源単独起動の安全性は、回路条件と
FC5V・IOVDD・M2・最初のベクタ応答を実測して判断する必要がある。

最初のROM読出しよりRPが遅ければ、このコードが後から自動的にCPUを救済できる
とは限らない。その場合はさらに早い起動経路（OTP等）やハード側の対策を検討する。
ツインファミコンで電源ON→自動再生を確認するまで、目標は完了扱いにしない。
