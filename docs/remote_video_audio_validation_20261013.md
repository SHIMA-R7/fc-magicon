# 連続カラー表示・音声・通信負荷の検証

2026-10-13。実機への書込みはしていない。提供されたブルアカのスクリーンショットをパンさせ、フレーム番号と動くバーを重ねた6秒・180枚の合成素材を使用。実ゲームや実動画を録画したものではない。音は独自に生成したテスト音。

## 連続表示

RetroArch用Nestopiaコアをlibretroフロントエンドから駆動。検証用コアはエミュレーターの走査線情報から画像位置を選び、元の全面フレームバッファを直接読む。これは実機の位置検出やPIO応答を再現するものではない。

6502ドライバーは実際の元の全面表示版を使い、パレット・属性をSRAMに渡した。180枚を30fps相当（エミュ上は60Hzで各画像を2回）で更新。360表示フレームすべてで、変換画像とのRGB画素差は0。動画の右側は実際のNestopia描画結果。

- `firmware/sim/retroarch-remote-20261013/video-load/color-video-nestopia-30fps.mp4`：左が合成入力、右がNestopia。音は元のテスト音を付けたもので、NESのAPUや実機の出音ではない。
- `.../color-audio-transport-model.mp4`：下記の分割送信・650,000B/秒を仮定した通信モデルの表示時刻と、実際のCリング処理から取り出したPWM相当音声を再生。映像表示は受信バイトをソフトウェアで描画したもの。こちらはRetroArchの描画動画ではない。

変換は実際の `nesframe.encode(..., color, prev=..., iters=2)`。180枚のカラー変換時間は平均26.90ms、95パーセンタイル35.20ms、最大53.09ms。33.33msを超えたのは13枚。音声PCM16のパケット化は平均0.077ms。キャプチャ時間は含めないため、この数字から実機の30fpsを保証しない。

## 現在のタイル圧縮方式の混在

実際の `remote_full.h` をDLLとして実行し、6502ドライバーと同じ128バイトずつ・8表示フレームでNTをコピーするモデルで比較。初期画面はコピー済みとして、起動途中の乱れを除いた。

30fpsで更新すると360表示フレーム中357で、即時にNTを切り替えた場合との差、または属性表の混在が発生。追加の最大差は22,270ピクセルの**色番号**。256タイルへの近似だけでも平均7,180ピクセルの色番号が変わる。これらは色番号の差であり、同じRGB色に割り当てられた番号の違いを含む可能性がある。

したがって、分割送信を追加した実機用UF2も、きれいな30fps動画と同じ画質になる版ではない。全面フレームバッファを高速に返す実機側方式と、画面・パレット・属性の一貫した更新を今後実装・検証する必要がある。

## 映像・音声の同時送信

PC側は実際の `IoThread`、カラー変換、PCM16パケット生成を使用。カセット側の `audio.c` は、DMA/PWM初期化と読出し位置だけをホスト用に置換し、リング、無音埋め、100msの先行書込み、過剰時の破棄をそのまま実行。32kHzで進む時計を与えた。

通信は偽ポートで仮定の帯域を与え、次の60Hz境界で画面交換するモデル。USB/TCP/ESP32の実測ではない。WindowsのスケジューリングとPythonの処理時間も結果に影響する。各試験の素材は6秒。受信フレーム数には終了直後に届いた保留分も含む。

| 仮定帯域・要求fps | 方式 | 受信画像数 | 受信音声サンプル | リングが捨てた音声 | 10ms以上の無音 |
|---|---|---:|---:|---:|---:|
| 650,000B/秒・30fps | 従来 | 121 | 192,000 | 0 | 0回 |
| 300,000B/秒・15fps | 従来 | 72 | 192,000 | 0 | 0回 |
| 120,000B/秒・30fps | 従来 | 21 | 192,000 | 21,760 | 8回、最大141.72ms |
| 650,000B/秒・30fps | 1KiB分割 | 95 | 192,000 | 0 | 0回 |
| 120,000B/秒・30fps | 1KiB分割 | 18 | 192,000 | 0 | 0回 |
| 120,000B/秒・3fps | 1KiB分割 | 18 | 192,000 | 0 | 0回 |

分割方式は低帯域で音声を守れた。一方、今回の高帯域モデルでは画像数が減っており、1KiB分割と頻繁なI/Oの負荷を含めて今後調整が必要。画質も含めた実機での30fpsは未達。

単純な帯域下限：映像1枚15,463バイト×30fps + PCM16約64KB/秒 ≈528KB/秒。通信・フレーム待ちの余裕は別に必要。低帯域では映像を間引く必要がある。

## 実装した対策

従来の `FCFR` と音声 `FCAU` を維持し、新しい `FCCH` を追加。`FCCH` はoffset・length各16bitと最大1,024バイトのデータ。PCは映像チャンクの間に音声を優先して送れる。開始した画像は途中で新しい画像へ取り替えず、全チャンクを送り切る。

受信側は連続offsetを確認し、全15,459バイトがそろったときだけ画像をコミット。欠落、順序違い、範囲外、部分受信ではコミットしない。offset 0から次の画像を開始できる。画像・99バイトの付随データの組立てを `remote_chunk.h` に分離し、実際の共有実装で100画像、境界、欠落、回復を試験して合格。

PC側は `remote_pc.py --chunked` で選択。**新しい受信ファーム専用**で、古いファームにはこのオプションを付けない。既定は従来方式なので、現在の実機に対する互換性を維持。

未書込みの実機用ビルド：`firmware/out-direct-pio-diagnostic/magicon-remote-full-smallcursor-chunked.uf2`。小さいカーソル・分割受信対応を含む。RP2350ビルド、Python構文確認、共有Cの組立て試験は成功。

- `generate_video_sequence.py`：入力作成・PC変換時間

- `test_av_transport.py` と `--chunked`：従来／分割送信の同時負荷
- `test_full_tile_updates.py`：現在のタイル圧縮・NT更新混在
- `render_video_results.py`：動画化
