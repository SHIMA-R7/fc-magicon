# 転送音声の実機診断

音声監視版は10月14日に書き込み・Flash検証完了。`watch_audio_probe.py` でFCドライバ進行を確認後、640サンプルのPCM16（440Hz、振幅6000）を20ms周期で5秒送信。

受信・受理は251パケット（250音声＋最後の無音）で一致。DMA読出し進行は約32kサンプル/秒、送信中の先行量3393〜3462サンプル。PWM比較値は変化し、GPIO44のFUNCSEL=4（PWM A10）、OE有効、出力と入力PADの高低もログに現れた。音が実際に適切なアナログ波形で出たことはこのログだけでは証明できない。

ユーザーは初め無音、VR1調整後に小さな「ポポポ」という音を確認。振幅を6000→24000にしても「ポポポ」のまま。F1レース・マリオの本体APU音は正常だったとの回答。本体APU経路とRP2350のPWM混合経路は異なるため、APU音が正常でもPWM経路の正常性は保証しない。

次の比較版はPWM自体を440Hz・50%デューティに設定し、サンプルDMAを停止してUSB音声送信を使わず連続音を出す。RC以降は同じ。UF2は `magicon-remote-direct-tone-20261014.uf2` に保存しビルド成功、未書き込み。起動してリモートモードに入ると継続して鳴る診断専用版で、通常の動画PCM再生用ではない。

比較用ソースは `C:/Users/Yugo/pico/work-remote-audit-20261014`。`FC_AUDIO_DIRECT_TONE` のターゲット定義で有効化。現在Flash上は音声監視版で、直接音版ではない。ログ: `firmware/sim/audio-hardware-20261014/audio-probe.log`。

その後、直接440Hz PWM版を書き込み・検証し、ユーザーが「成功！」と確認。低周波PWMの経路で音を出せることは確認できたが、244kHzキャリアを平滑化したPCM出力の品質まで保証する結果ではない。

次の固定リング版は通常と同じ32kHz DMA・TOP1023のPWMを使い、8192サンプルに112周期の矩形波（437.5Hz、PWM値256/768）を事前に置き、USB補充と再生済み領域の消去を行わない。これでUSB/補充処理とDMA/高速PWMを分ける。`magicon-remote-fixed-ring-tone-20261014.uf2` をビルドして保存。`FC_AUDIO_RING_TONE` の定義で有効化する診断専用版。現時点で未書き込み、Flash上は直接440Hz版。

固定リング版を書き込み・検証したところ、ユーザーは「断続的な音」と報告。したがってUSB受信とリング補充・消去を除いても症状は残る。DMAのリング境界はELFのringアドレス0x20010000で16KB境界、CTRLのRING_SIZE=14、RING_SEL=readで整合していた。

公式RP2350データシートのnarrow IO write節も確認。16ビット書き込みは32ビットバスに値が複製される仕様で、これ自体をバグと断定しない。次の比較では32ビット配列・DMA_SIZE_32・32KB読出しリング（ringは引き続き0x20010000）でAチャネルだけ明示的に書く。サンプル数8192、32kHzペース、TOP1023、437.5Hz波形は同じ。`magicon-remote-fixed-ring-word32-20261014.uf2` に保存、ビルド成功、未書き込み。

参照: https://datasheets.raspberrypi.com/rp2350/rp2350-datasheet.pdf §2.1.5。

32ビット版を書き込み・検証。ユーザーは「より高速な断続音」「断続のピッチは固定ではなく早くなったり遅くなったりする」と報告。16ビット書き込みだけを原因とする説明は支持されない。

波形測定版を書き込み・検証し起動。PIOの262.144ms・1048576サンプル記録で64000立上り、キャリア周期16〜17サンプル（4MHzサンプル、約244kHz）、記録中の長いキャリア途切れはなし。1ms窓262個のHIGH率は24.975〜75.025%。FFTの最大成分は438.93Hzだが、周辺にも成分があり、短時間・1ms平均データからPCM更新ジッタやRC後の音を確定しない。`gpio44-wave.log` に保存。

次の優先度比較版は、同じ固定32ビットリングと波形測定を保ち、音声DMAだけhigh_priority=trueにする。CHR応答もDMAを使うため、競合の影響を比較する仮説検証であり確定修正ではない。`magicon-remote-audio-priority-20261014.uf2` をビルド・保存、未書き込み。

優先度版を書き込み・検証したが、ユーザーは断続音のままと回答。波形記録のキャリア周期も16〜17サンプル、64000立上りで同じ。優先度変更は解決策として採用しない。

次の搬送波比較版は固定32ビットリングと32kHzサンプルレートを保ち、PWM_TOP=255、SILENCE=128、矩形波の比較値64/192にして25/75%のデューティを保つ。キャリアは250MHz/256=976562.5Hz。DMA優先度は元のlowへ戻す。PWM分解能が10→8ビットになるため精度とのトレードオフがある。高速PWMの平滑化・音声経路との相互作用を調べる仮説検証であり、回路不良の断定ではない。`magicon-remote-audio-carrier8-20261014.uf2` をビルド・保存、未書き込み。

搬送波版も実機で症状変わらず。波形測定では256000立上り、周期4〜5サンプル。低周波直接音は正常だが、DMAでPWM比較値を更新する方式の問題は残る。

その後ユーザーのOFF回答を受け、244kHz・固定32ビットリングへ戻し、測定の経過実時間とPIO RX stallおよびデューティ状態切替間隔を追加した詳細測定版を書き込み・検証。結果: 262145us、RX stall=0、64000キャリア立上り、デューティ状態の切替230回、間隔3908〜4695サンプル（4MHz、約0.977〜1.174ms）。440Hz付近の半周期にばらつきがあり、観測中の記録側stallでは説明されない。ただしこの結果のみでDMA競合などの根本原因を確定しない。

次はPIO2 SM2がGPIO44へPWMを直接出す比較版。1サンプルを12キャリア周期保持し、1サンプル6206命令サイクル、FIFO8ワード＋OSRで先行補充する。DMAはPWM CCレジスタではなくTX FIFOを満たす。8ビットデューティ、キャリア約384kHz、サンプル目標32kHz（PIO divider量子化による僅かな差あり）。固定リングの437.5Hzテストで確認する。`test_audio_fifo_timing.py` で全256値の実行時間6206サイクル一定・デューティ単調・全32ビット消費を確認。RPビルド成功、`magicon-remote-audio-pio-fifo-20261014.uf2` に保存、未書き込み。

PIO FIFO版を書き込み・検証し、ユーザーは「ピーという連続音になった」と確認。詳細測定でも初めの途中周期を除いて状態切替間隔は主に4496/4621〜4622サンプルの規則的な2値となった。連続音の実機成功を確認した基準UF2として保存する。DMA→PWM CCの方式より改善したことは確認できたが、ハードウェア競合のどの部分が原因だったかまで断定しない。

USB PCM入力へつなぐ次の比較版は固定リングモードを解除し、初期無音128・PCM16から8ビットPWMへの量子化（右シフト8）で通常の補充と消去を再開する。PIO波形の自動測定は無効にし、262msブロックがストリームに混ざらないようにする。`magicon-remote-audio-pio-pcm-20261014.uf2` をビルドして保存、未書き込み。

実験ソースは `firmware/experiments/audio-pio-20261014` に保存。最近のNSF基幹ソースへはまだ統合していない。ビルドではaudio_fifo.pio/audio_sample.pioのPIOヘッダ生成と `FC_AUDIO_FIFO_TONE=1` が必要（このマクロはバックエンド選択で、固定音にするには別途 `FC_AUDIO_RING_TONE` が必要）。mainにはaudio_debug_reportの宣言と1秒周期呼出しを追加する。

USB PCM版を書き込み・検証し、起動後に440Hz、振幅12000のPCM16を5秒転送。受信251・受理251で一致、読出し進行は約32040サンプル/秒（PIO divider量子化の影響）、GPIO44 FUNCSEL=8（PIO2）。ユーザーが「成功！」と確認。固定波形だけでなく、USB受信・補充・PIO出力の組み合わせでも連続音が鳴ることを実機確認した。

次にユーザーの指示で、改善した8fps・240枚の冒頭30秒動画をPCM16音声付きで転送開始。静止画成功と音声単独成功から、動画＋音声同時動作の確認へ移行。

最初の同時再生はユーザーから無音・映像の乱れと報告。診断を付けて再送したログでは音声受信・受理数は一致し、音声先行量は約2900〜3900サンプル残っていた。素材WAVを調べるとピーク1249/RMS267.9（PCM16）と小さかった。送信前の素材音量確認が不足していた。

`replay_video_clip.py --audio-gain 20` を追加。素材はピーク24980となり、959776サンプル中クリップ0。PIO PCM版で8fps動画・音声同時に再送し、ユーザーは「聞こえた」「なってる」と音楽の再生を確認。240枚の最終書込完了・8.0枚/秒。映像の乱れは未解決。

ユーザーが画質優先で4fpsへ落とすよう指定したため、同じ8fps事前変換素材から時間位置に応じて間引き、`--fps 4 --source-fps 8 --audio-gain 20` で30秒の同時転送を開始。音声の時間刻み20msは変更しない。画素変換は同じで、更新途中の混在をなくす変更ではなく、更新頻度だけを減らす比較。

次はGPIO44のPWM muxを維持したままPIO2 SM3で入力を4MHzサンプルし、DMAで1048576ビット（約262ms）を記録する。キャリアの立上り間隔最小/最大と、1msごとのHIGH数を出力。RC後のアナログ信号・テレビ音は測らない。固定リング32ビット版に測定を追加した `magicon-remote-audio-wave-probe-20261014.uf2` を準備しビルド成功、未書き込み。結果は `watch_audio_wave.py` で取得する。
