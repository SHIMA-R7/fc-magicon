# 静止画の画質改善（2026-10-13）

現在の実機は256種類の背景タイルを保持するリモートFW。送信前にパレットのLab距離を用いて256種類へ近似すれば、実機の頻度優先・ビット距離による二度目の近似を回避できる。

`firmware/tools/tile_quality.py` は、各パターンが使われる属性パレット別の頻度を数え、表示色の誤差を最も減らすパターンを順次選ぶ。採用済みパターンへの置換も表示先のパレットで評価する。現時点ではオフライン実験用であり、常時リモート取り込みの既定処理には組み込んでいない。

色変換は背景候補4色、探索8回、属性の平滑化罰点0で試し、ディザ振幅48/24/0を比較。試した5/10/20秒地点はいずれも振幅0の最終Lab二乗誤差が最小だった。点模様を減らすため、中間色の表現にはトレードオフがある。

| 地点 | 従来の最終Lab MSE | 改善候補 | 減少率 |
|---|---:|---:|---:|
| 5秒 | 149.31 | 113.84 | 23.76% |
| 10秒 | 118.13 | 110.61 | 6.36% |
| 20秒 | 287.27 | 230.34 | 19.82% |

元動画の256×240 RGBとの比較。従来値も改善値も実際の `remote_full.h` をコンパイルしたDLLで再構成し、属性とパレットを付けた静止画で測定。改善候補は全3場面で送信画像と再構成画像のRGB差0を確認。これは実機画質・動的更新の保証ではない。

処理時間は候補により約0.05〜1.08秒/枚。30fpsには不足している。動画用には処理の高速化、パターン集合の再利用、フレーム間のパレット変動抑制、8フレームに分けたネームテーブル更新への対策が必要。

5秒地点の改善静止画をCOM11経由で40回提供し、10856バイトの受信を確認。実機の表示完了ACKはない。ファームウェアやROMの書き換えは行っていない。

ユーザーが実機写真とともに「成功！」と確認。髪や水面の大きなブロック崩れが減った静止画版を成功基準として保存する。写真に残る縞・色の波について撮影由来か信号由来かは未判定。動画の滑らかさ、フレーム更新中の崩れ、全場面の画質は未確認。

## 同方式による30秒動画の実機転送

`prepare_quality_clip.py` で元動画の冒頭30秒から8fps・240枚をオフライン変換。ディザなし、初回背景候補4色、以降は前のパレットから探索2回で色の変動を抑制し、各フレームを256タイル以内にする。全240枚について実際の `remote_full.h` DLLによる再構成RGBが送信前画像に一致した。これは更新途中の画面の検査ではない。

変換は平均0.664秒/枚、最大1.503秒/枚。現在の実装ではライブ取り込みを8fpsで行えないため、先に全フレームを変換した。

`replay_video_clip.py --fps 8 --source-fps 8` でCOM11のFCドライバのフレームカウンタ進行を確認後、PCM16音声とともに30秒転送。ホストが提供した240枚すべての最終チャンク書き込みが完了、8.0枚/秒、総書き込み5,672,219バイト。実機での表示fpsや音声品質は測定していない。ユーザーによる再生画質・更新崩れの確認待ち。

`quality-8fps/quality-preview-30s.mp4` は変換結果を8fpsで並べた音声付きプレビュー。実機録画ではなく、8フレームのネームテーブル更新や信号品質の影響を含まない。
