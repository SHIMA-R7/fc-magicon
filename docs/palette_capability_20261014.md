# パレット読み出しの対応性検査

前のパレット比較はLED3回だったが、PPUリビジョンの直接読み出し対応を確認していなかった。今回は既知の2色に対して読み出しが追従するか、裏側のNTデータが返るかを分ける。

初回のフレーム転送完了後、2回のVBlankで以下を行う。

1. CIRAM $2F00〜$2F1Fに$05を保存する。
2. 全パレット32エントリーを緑$1Aに設定する。
3. $2F00を2回読んで遅延読み出しバッファを$05にする。
4. $3F00から32回読む。下位6ビットを色$1A・下層NT値$05・その他に分類する。
5. 青$12でも同じ検査を行う。

64読みすべてが設定色に一致すれば直接読み出し対応と整合、64読みすべて$05なら旧式のバッファ読み出しと整合、それ以外は判定保留。PPUの刻印を確定する試験ではない。旧式パターンであっても、画面の色切り替えを目視確認するまでパレットへの書き込み成功と断言しない。

- LED1回：直接読み出し対応と整合。
- LED2回：非対応PPUの読み出しと整合。
- LED3回：その他の結果で判定保留。

判定後も画面全体を約1秒おきに緑・青へ切り替える。LEDと色の両方を報告してもらう。元動画の再生・音声出力は行わない。

結果コード$5F20は2/3/4、$5F24/25/26に設定色/下層NT/その他の一致数を保存。実Cと6502・PPUモデルで、対応型64/0/0・旧式0/64/0・意図的な読み出し異常0/0/64の判別と、判定後120VBlankの色切り替えを検証した。最大NMI1809サイクル。

生成：`gen_video_driver.py baseline/palette_capability_driver.h --palette-capability`

ビルド：`build.ps1 -ColdBoot -PaletteCapability`

UF2：`firmware/out-standalone-video/palette-capability-cold-20261014.uf2`

SHA256：`a1d44056a8dac5e7e24bada1d76497849655fad030f6aae891747f2e29f2d747`

ユーザーのBOOTSEL／FC OFF確認後、EF5E4EB554097CDFへ書き込み・照合・アプリ再起動を実施。実機結果は未確認。

## 実機結果

ユーザー報告：「一回点滅で、青と緑の切り替えも成功してる」。この検査では64読みが設定色に追従する対応型の判定で、既知の全画面色の書き換えも成功した。前回のパレット不一致を単に読み出し非対応として除外しない。PPUリビジョンの型番までは未確定。

次は、通常フレームのパレットについて読んだ16色と、CPUが読んだ期待値・元の保存データを比較する。検査完了後にUSBを起動してログを出し、検査途中にUSB処理を追加しない。
