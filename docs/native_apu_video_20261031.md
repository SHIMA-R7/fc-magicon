# 動画と本体APUの同時再生試験（2026-10-31）

## 方式

ユーザー提供のピアノMIDIを、矩形波2音と三角波1音のレジスター列に変換する。
MIDIチャンネル10の打楽器があればノイズ音へ割り当てるが、今回の素材にはない。
各時刻の最高音を主旋律、最低音を低音、残る最高音を伴奏に選ぶ暫定編曲。
歌声・歌詞は再生しない。GPIO44のPCM出力は開始しない。

`firmware/tools/midi_to_apu.py` が59.94Hzの14バイトレコードを生成する。
12個のAPUレジスター値と12ビットの変更マスクを含む。
音程が変わらないフレームでは高位タイマーを書き直さず、矩形波の位相リセットを避ける。
同じ音高の弾き直しでは明示的に再トリガーする。

RP2350はSRAMに1レコードを用意し、6502が `$5C00–$5C0E` から読み出す。
6502はNMI内で必要なAPUレジスターだけ書き、`$5F14` に完了を返す。
完了まではRP2350がレコードを変更しない。
処理待ちでレコードを飛ばす場合は、その間の変更マスクをまとめて送る。
動画と演奏は同じ経過時間に従う。DMC DMAは使用しない。

## 素材と同期

- MIDI: ユーザー提供ファイル。約228.473秒、2,246ノート。
- 動画: 既存の全編8fps、1,939フレーム、242.375秒。
- MIDIの時間伸縮: 1.0倍。
- MIDI全体の開始オフセット: +9.8秒。
- 最初の音符: MIDI内約4.218秒なので、動画開始から約14.018秒。
- 同期値は原音声とMIDIのピッチクラス相関から推定。聴感確認は別途必要。
- 演奏レコード: 14,291フレーム、約238.422秒。末尾に明示的な消音を含む。

著作物のMIDI、変換済み楽曲ヘッダー、動画、結合UF2は公開ソースに含めない。

## 公開ソースからのビルド

既存のpico-sdk／RP2350ツールチェーン設定を使用する。
Pythonに`mido`をインストールし、自分が利用できるMIDIを外部ヘッダーに変換する。
以下のオフセット0は例であり、今回の曲に使った9.8秒を全素材へ適用するものではない。

```powershell
python -m pip install mido==1.3.3
python firmware/tools/midi_to_apu.py C:/fc-assets/song.mid C:/fc-assets/apu_score.h --offset 0
cmake -S firmware -B C:/fc-build/apu -G Ninja `
  -DFC_STANDALONE_VIDEO_ONLY=ON -DFC_PLAYER_COLD_BOOT=ON `
  -DFC_PLAYER_A9_REMAP=OFF -DFC_MEDIA_OFFSET=0x100000 `
  -DFC_PLAYER_APU_STREAM=ON `
  -DFC_PLAYER_APU_SCORE_HEADER=C:/fc-assets/apu_score.h
cmake --build C:/fc-build/apu --target magicon_standalone_video
```

APUモードでは制御レジスターの高速応答も自動的に有効にする。
6502ドライバーはビルド時に生成し、楽曲ヘッダーはリポジトリへコピーしない。
動画のFCPVは別途用意し、指定したFlashオフセットへ配置する。
ファームUF2単体には動画データを含まない。
公開用に整理したビルド経路のコンパイル検査と、実機で成功したスナップショットの試験は区別する。
公開予定のソースからAPUモードと従来PCMモードの両方をクリーンにビルドし、成功した。
公開用の整理後に実機へ再書き込みはしていない。現在の実機には全編試験を完走した版を保持している。

回帰テストは`firmware/tests/`の以下を実行した。

- `test_midi_to_apu.py`: 音符、サステイン、テンポ、再トリガー、消音。
- `test_apu_video_driver.py`: 生成した6502コードの演奏書き込みとNMIサイクル数（`py65`を使用）。
- `test_player_fast_control.py`: 実際のC関数の制御読み書きとbankのACK（Zig Cを使用）。
- `test_player_ppu_deadline.py`: PIOの期限切れ返信、ゼロ方向返信と復帰。
- `test_adpcm_video.py`: CとPythonのADPCM一致、リング折り返し、末尾消音、形式検査。

## 横縞の切り分けと制御レジスターの応答修正

最初の実機録画の0:42.5付近に、保存フレームに存在しない横縞を確認した。
同じファームの再試験でも発生。本体APUへの書き込みだけ止めても残り、
音楽を動かしたまま静止画を固定した試験では600録画フレームに横縞を見つけなかった。
CHR書き込みに間隔を追加する試験でも解消しなかったため、その変更は取り消した。

一方、`INC $5F0F`で更新するフレームカウンターは、毎秒ほぼ`$60`付近に留まっていた。
`$5Fxx`の制御読み出しが高速応答の対象外になっていた。
応答が間に合わず命令の上位オペランド`$5F`が読まれた場合、INC結果が`$60`になることと整合する。
これは実機タイミング上の推定であり、オシロスコープでバスを直接測定した結果ではない。

`$5Fxx`を高速関数へ追加して読み出し時にready/bankを計算するだけの比較版は、
実機で次フレーム待ちのタイムアウトを起こした。
最終比較版では、データ・方向・有効フラグを含む32ビット返答をSRAMに事前生成する。
カウンターや入力の書き込み時に返答を更新し、`$5F10`のready/bank値は
画像の準備完了時と正しいbankのACK受信時だけ更新する。
これにより実機カウンターが毎秒約60/61増分で進むようになった。
同じ問題箇所の再録画では横縞を認めなかった。

一般ソースの比較用スイッチは`FC_PLAYER_FAST_CONTROL=ON`。
既存設定ではOFFとし、現時点では通常の単独動画再生で使用する。
デスクトップや別診断への適用には、そちら固有のメールボックス更新も追従させる必要がある。
ホスト回帰テスト`test_player_fast_control.py`は実際のC関数を抽出してコンパイルし、
1,000回のRMW、両bank、誤ったACKの拒否、正しいACKによる解放を確認する。
ホスト試験だけではM2締め切りを確認できないため、実機試験と併用する。

修正版の実機ログ・録画の接頭辞は`apu-noise-fixed-full-g`。
変更前のログにfaultがないことだけで、映像が完全に正常だったとは判断できない。

最終試験は248秒実行し、全1,939コマ・楽曲末尾の消音まで到達した。
244個の毎秒カウンター記録で増分は60または61となり、faultログはなかった。
39〜44秒の対応場面を確認し、変更前に出ていた横縞を認めなかった。
全録画フレームの網羅的な画像一致判定は行っていない。
試験後はDP100出力をOFFにし、出力0V・0mAを確認した。
レビュー用MP4はローカルの`INMU-KING-native-APU-fixed.mp4`（4分8.2秒）。
