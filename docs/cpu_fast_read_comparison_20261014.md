# CPU応答を短くする比較版

パレットログで保存元とFC取得値に差を確認したため、同じ診断・同じ映像データのまま、CPU応答経路だけを比較する。

`FC_PLAYER_FAST_READS` を有効にすると、コア1が読み出し要求を受けた後、ROM・$6000〜$63FFのNT・$5D00〜$5D1Fのパレットを専用経路で返す。通常の統計更新・汎用分岐を通さない。パレットは各転送前に返信用32bit値を準備し、コア1で表裏ポインタを追わずに返す。返信表はCPU応答ループと共にSRAM配置。

書き込み、および書き込みデータ待ちの状態は従来処理に渡す。起動ハンドオフ・PIO・クロック・PPU側・診断ROM・パレット生成は変更していない。読み出しの高速化は処理経路短縮という設計意図であり、実機の応答時間は未測定。

ホスト試験では65536アドレスすべてで専用経路の選択範囲と従来の返却値が一致すること、書き込み/書き込み待ちを横取りしないことを検査。初期化時と各12フレームのステージ後に実施。実C/6502の全フレーム照合・ログ保存、意図的なパレット不一致の検出も通過。NMI側最大1800サイクルはFCプログラムの値であり、RPの応答速度を測った値ではない。

ELF上：remote_bus_loop=0x200006A0、rd_palette_replies=0x200192A0。

ビルド：`build.ps1 -ColdBoot -PaletteLog -FastReads`

UF2：`firmware/out-standalone-video/palette-log-fast-cold-20261014.uf2`

SHA256：`f219c6648e1a936008e372e20341001647c0d5d5ee944d7e670c0619f41c4a2a`

USBは検査完了後のみ起動。次の実機ログは元のログと区別するファイル名で取得する。現時点で未書き込み・実機未検証。

## 実機結果：診断成功

OFF/BOOTSEL確認後に書き込み・照合・再起動を実施。ユーザー報告はLED1回、色も改善し、写真から大きな黒い矩形の解消を確認。COM11から `palette-log-fast-hardware-20261014.json`/`.log` を取得。

status=2、frame=11、palette_errors=0。12枚のNT・パレット照合を完走し、最後の16色はtarget=expected=actualの全一致。以前の版はframe=0で停止し、expectedとactualの比較で10不一致だった。

同じ診断・映像データでCPU応答経路を変えると一致したため、応答時間不足という仮説を強く支持する結果。物理信号の時間余裕や、長時間の通常4/8fps・音声同時再生まで実証したものではない。診断成功版UF2とログを保存し、次に通常の30秒4fps・音声付き版へ同じ修正を反映して確認する。
