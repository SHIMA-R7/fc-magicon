# 2コンマイクのADC録音試験（2026-11-24）

## 実装

- ESP32-C6 GPIO0 / ADC1 CH0で16 ksample/s、12 bitの連続変換を行う。
- 2秒分をRAMへ保存してからUARTへ送る。115200 baudでのリアルタイムPCM送信は行わない。
- 指示が届くまで録音しない。GPIO0を出力にはしない。
- C6のRGB LEDは起動時に消灯する。
- 既存のUSB/Wi-FiブリッジとSWD機能を残す。録音中は通常ブリッジのループ処理が止まるため、転送中のクライアントがある場合は録音を拒否する。

対象ソースは `firmware/wifi_bridge/mic_diagnostic.h`、PC側は `firmware/tools/capture_fc_mic.py`。

## UART操作

CH343側UARTで、115200 baud、DTR/RTSを非アクティブにして接続する。
要求は `0x03` に続けて `MIC1 2000\n`。録音時間は100～2000 ms。

応答は以下の順序になる。

1. `MIC1 CAPTURING ...` の開始通知。
2. `MIC1 {...}` のJSON行。サンプル数、バイト数、DC電圧、最小値・最大値、ADCプールオーバーフロー数、変換所要時間、FNV-1aを含む。
3. 指定バイト数のunsigned 16 bit little endian配列。各値は0～4095。
4. `\nMIC1 END\n`。

PC側は長さ・終端・チェックサム・オーバーフローを確認して保存する。
WAVはDCを除去し、12 bit値を固定倍率16で16 bitへ変換する。自動音量正規化はしない。

```powershell
python firmware/tools/capture_fc_mic.py --port COM12 --out mic-test
```

COM番号は実機の識別情報で確認する。C6のネイティブUSBはRP2350との接続に使うため、この診断にはUART側を使う。

## 実機結果

ツインファミコンへの給電はDP100から7.5 V。試験中の実測は約7.50 V、339～342 mA。
試験終了時は出力OFF、0 V / 0 mAを確認し、PCの音量も試験前の値へ戻した。

- FC OFF時：DC約1.626 V、ノイズRMS約1～2 ADCカウント。ユーザーのテスター測定は1.59 V。
- FC ON、テスト音なし：RMS約135カウント。約146 Hzや5.054 kHz付近の成分がある。既存の本体音源などとの切り分けは未完了。
- イヤホンからの試験では、テスト音の受音を確定できなかった。
- スピーカーへ変更し、2コンのマイク音量を最大にすると、1 kHzおよび500 Hzのテスト音がADC録音の主成分になった。音響入力からC6の記録までの経路を確認できた。
- PC音量25%では多数のADC下限到達が発生。5%へ下げると大幅に減ったが、短い下限到達は残った。
- 全試験で32,000サンプルの受信・チェックサム照合に成功し、ADCプールオーバーフローは0。

FFT上のテスト音は公称16 ksample/sで約998.5 Hzおよび499 Hzとなった。
サンプルクロックの誤差を含むため、この差だけで音源の周波数異常とは判断しない。

この段階で確認したのは2秒録音。連続Wi-Fi音声送信、通話、エコー処理、音声と本体音源の分離は未実装・未検証。
受動入力回路の直列抵抗値や最大入力電圧は、録音できたことだけでは保証できない。

既存Wi-Fi資格情報やフラッシュのバックアップは公開しない。
