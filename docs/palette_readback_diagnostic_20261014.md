# 各フレームのNT・パレット照合

前回の12枚NT照合は実機でLED1回だったが、最後の画像には保存画像にない黒い矩形が残った。今回は同じ12枚を同じ速度で転送し、NT1024バイト一致後、背景パレット16エントリーをPPU $2007から読む。

パレット読みはNT/CHRと異なり遅延バッファを捨てるダミー読みを入れない。上位2ビットをマスクし、6ビットの色番号をCPU $5D00〜$5D0Fの期待値と比較する。PPUMASKは従来の$0Aでグレースケールなし。検査後は通常のPPUアドレス・スクロール復帰処理へ進む。画面全体の判定色への塗りつぶしはしない。

- LED1回：12枚のNT・パレットが一致。
- LED2回：NT不一致のフレームで停止。
- LED3回：パレット不一致のフレームで停止。
- LED5/6回：従来の更新/検査完了の待機期限エラー。

約8秒＋起動時間。音声と音声DMAは停止。通常4fpsの再生条件そのものではなく、各フレームの検査後に次へ進む。

実C・6502・PPUモデルで12枚の一致ケースと、各フレームの背景パレット16エントリーをすべて意図的に変えた不一致ケースを検査し、完了コード2/4と0/16不一致を確認。パレット読み上位ビットを$C0にしてマスクも検証。最大NMI1800 CPUサイクル。ビルドと結合UF2からのデータ復元照合に成功。

生成：`gen_video_driver.py baseline/palette_readback_driver.h --palette-readback`

ビルド：`build.ps1 -ColdBoot -PaletteReadback`

UF2：`firmware/out-standalone-video/palette-readback-cold-20261014.uf2`

SHA256：`6da9198e114ef5795b373ed51313f17ca3bca2a2f02ea288a9c393f148761219`

ユーザーのFC OFF・BOOTSEL確認後、EF5E4EB554097CDFへ書き込み・照合・再起動を実施。実機の結果は未確認。

## 実機結果と診断上の制約

ユーザー報告はLED3回。NT一致後のパレット比較が不一致となり、その場面で停止した判定。写真は通路の人物の場面。

追加調査で重要な制約が判明した。NESdev PPU registersのPPUDATA説明では、パレット直接読み出し対応は2C02G・2C02H・PAL PPUとされる。実機PPUのリビジョンは未確認。この試験のPPUモデルは対応機種を前提としており、非対応の実機では偽の不一致を出し得る。

したがってLED3回だけで「パレット書き込み不良が黒い矩形の原因」と断定しない。対応性確認を先に入れるべきだった。次は既知のパレットと下層NTデータを区別する対応性検査か、読み出し対応に依存しない表示比較を行う。現在の試験には対応性検査が未実装。
