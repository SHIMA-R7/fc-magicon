# CPUデータ窓の比較診断

直前のFCローカル生成パターンは実機で全52試験・不一致ゼロだった。次に$6000～$63FFからRP2350側のデータを読み、FC自身が計算した正解と比較してから、その受信値をPPUのNTへ書く試験を追加する。描画・音声・NMIは引き続き無効。

各書き込み前にFCがパターン番号・バンク・要求連番を通知する。RPが1024バイトの固定パターンを生成し、メモリバリア後に準備完了を返す。FCはそれを待って読み出す。52試験、2バンクずつで104要求。次のデータへの更新はFCが現在の書き込みを終えた後だけ行う。

記録はCPU窓からの受信不一致（cpu_errors、cpu_xor_mask）とNT読み戻し不一致（errors、bit_errors）を分ける。NT読み戻しの期待値はRPから再度取得せず、FC自身の計算値を使う。CPUデータが間違ってもそのままNTへ書くので、その影響が読み戻しにも現れるかを比較できる。

レコード署名はC5（旧固定パターン版はA5）。従来の32バイト形式の28/31番をCPU不一致数、11番をCPU側XORマスクとして使用する。USB受信ツールは署名で解釈を分け、旧ログも読める。

生成：`gen_nt_stress.py baseline/nt_cpu_window_driver.h --cpu-window`

ビルド：`build.ps1 -ColdBoot -FastReads -CpuWindow`

UF2：`firmware/out-standalone-video/cpu-window-pin-audit-cold-fast-20261015.uf2`

SHA256：`8e2d1d76dabef84a7b28c1c6616c0b33887d7bb85945483b268933005bcfb1f5`

実C/6502検査では正常の52試験が不一致0、104要求が順序どおり完了。CPU窓の受信値だけをXOR 02で壊す故障注入では、CPU受信不一致2048回/試験、NT不一致4096回/試験、双方のXOR 02を検出した。合格/不一致の最終単色表示も確認。PIO・実電圧・描画中の競合はこの模擬検査の対象外。

ユーザーから「書き込みOK」、BOOTSELデバイスEF5E4EB554097CDFを確認。UF2だけを書き込み、picotool照合OK後に通常アプリへ再起動。実機結果は未取得。USBは全試験終了または60秒の期限後に開始する。FC ONの操作はユーザー側。

## 実機結果

ユーザー「2/赤」。USBログ `cpu-window-hardware-20261015.json` / `.log` を取得。全52試験完了、メールボックス異常0、CPU受信不一致0。NT不一致は最初の1試験だけ936回で、残り51試験は0。最初の試験はパターン00、バンク0、1巡目。先頭offset0で期待00に対し実値FF、ビット別不一致は全8ビットへ分布。4回の読み戻し合計936回であり、936個の異なるアドレスを意味しない。

この結果では恒久的な特定ビット故障より、最初の書き込みに特有の条件を先に検査する。PPUには起動直後のレジスタ書き込み抑止期間がある（[NESdevの実測に基づく記録](https://www.nesdev.org/wiki/PPU_power_up_state)）。今回それが原因と確定したわけではなく、従来のホストモデルはこの起動条件を再現していない。次は開始待ちを追加し、待った後に描画停止設定を再度書く比較を行う。
